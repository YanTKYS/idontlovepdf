## 1. 背景

自治体内で、一般職員（情報部門職員に限らない事務職員）が利用する「PDF編集ツール」を検討している。

想定する利用場面は次のようなものである。

- 起案文書や通知文のPDFに残った誤字を直したい
- 日付や金額など、PDF内の一部の文字だけを差し替えたい
- 元のWord等の原本が手元にない、または原本を追跡できないPDFを補正したい

利用環境の前提は次のとおり。

- Windows端末、庁内ネットワークまたは閉域ネットワーク
- 標準ブラウザ
- IIS等による静的ファイル配信
- 利用者端末への追加インストールは求めない
- 外部通信、外部API、外部CDNを前提にしない

この前提は `reference/guide_context.md`（`lg_toolkit_guide` の最小ガイド）に沿う。

## 2. 当初要件

主目的は次の1点である。

> **既存PDF内の本文テキストを直接編集すること**

具体的には、既存PDF内の文字を選択して、次の操作を行い、編集結果をPDFとして保存できることを想定している。

- 修正
- 削除
- 置換

### 2.1 「本文テキスト編集」に含めないもの

以下は、今回求めている「既存PDF本文テキスト編集」とは明確に区別する。

| 手法 | 今回の扱い | 理由 |
|---|---|---|
| テキスト追記（新規テキスト要素の追加） | 対象外 | 既存本文そのものは変わらない |
| 注釈（アノテーション）追加 | 対象外 | 本文レイヤーではなく注釈レイヤー |
| 白塗り＋文字の重ね書き | 対象外 | 見た目を繕うだけで本文が残る。検索・コピーで旧文字が露出する |
| フォーム入力 | 対象外 | フォームフィールドがあるPDFにしか使えない |

要件を白塗り＋重ね書きに下げて「PDF編集可能」と扱うことはしない方針とする。

理由は次の2点である。

1. 旧文字がPDF内部に残るため、文字検索・テキストコピー・別ビューアでの表示で旧内容が露出しうる
2. 自治体文書として、見た目と実体が異なる状態を職員向けツールで量産すべきではない

### 2.2 今回の対象外機能

次のページ編集機能は、今回の検討対象に含めない。

- ページ回転
- ページ挿入
- ページ削除

### 2.3 別扱いとするもの

- 画像だけで構成されたスキャンPDF（OCRを必要とするため、本文テキスト編集とは分けて考える）

## 3. 初回検討（第1段階）

当初は、一般的なOSS JavaScriptライブラリを中心に検討した。

主な検討対象は次のとおり。

- PDF.js
- pdf-lib

### 3.1 これらで実現できること

- PDFの表示
- PDFの生成
- テキストの追加
- 注釈の追加
- フォーム入力
- 既存ページへの描画

### 3.2 これらで実現できなかったこと

既存PDF本文のテキストを、一般職員がWordに近い感覚で直接編集する用途には適さない。

技術的な理由は次のとおり。

- PDFの本文は「文字列」ではなく、フォント参照・座標・描画命令の集合として保持されている
- そのため「この文字を1文字消して別の文字を入れる」という操作が、既存ページ内容ストリームの再構築を伴う
- 段落・行・文字送りの再計算をライブラリ側が提供していないため、編集結果のレイアウト整合を自前で担保する必要がある
- 埋め込みフォントのサブセット（使用文字だけを埋め込んだ状態）では、新しく入力した文字のグリフが存在しないことがある
- 日本語では文字種が多く、サブセット問題の影響が大きい

これを自前で実装すると、事実上PDFレイアウトエンジンを作ることになり、庁内の小規模内部ツールとして保守できる規模を超える。

## 4. 初回判定

上記を踏まえ、初回は次の結論とした。

> **当初要件のままでは、静的Webツールとして運用困難**

補足として、次を方針とした。

- 白塗り＋重ね書き等に要件を下げて「PDF編集可能」と扱わない
- 要件を維持したまま、いったん保留とする

## 5. 再検討の理由

初回判定の後、次の疑問が残った。

> 「既存JavaScriptライブラリを利用する前提でも、本当に不可能なのか」

初回検討の調査範囲は、実質的に **OSS・無償ライブラリに限定** されていた。

つまり初回判定は、
「PDF本文編集が技術的に不可能」ではなく、
「**調査した範囲に、それを実現する部品が無かった**」という判定だった可能性がある。

そこで、調査範囲を次まで広げて再検討した。

- OSSに限らない
- 商用のWeb向けPDF SDK（JavaScript / WebAssembly）を含める

## 7. 候補SDK

### 7.1 Apryse WebViewer（第一候補）

公式情報上、Content Edit 機能により次が可能とされている。

- 既存PDFテキストの直接編集
- テキストの移動
- テキストの削除
- 画像の編集
- 編集後PDFの保存

構成面での適合性は次のとおり。

- WebAssembly等を利用し、PDF処理をクライアント側で行う構成（client only モード）が用意されている
- クライアントのみの構成では、静的WebサーバーでHTML / JavaScript / CSS を配信し、ブラウザ内でPDFを処理する方式が正式に案内されている
- サーバーサイドの変換処理を必要としない

今回の「静的Webツール」「閉域前提」という構成との適合性が高いため、**現時点の第一候補**とする。

留意点は次のとおり。

- Content Edit は追加ライセンス対象（既存のWebViewerライセンスキーに含まれない扱い）とされているため、採用時にライセンス条件の確認が必要
- Content Edit モードのテキスト編集パネルで正しくフォントを表示させるには、フォント定義（`font.json` 等）側の条件を満たす必要があるとされる

参考（作業時に再確認すること）:

- <https://docs.apryse.com/web/guides/edit/text-edit>
- <https://docs.apryse.com/web/guides/deployment-options>
- <https://docs.apryse.com/web/faq/webviewer-on-static-server/>
- <https://docs.apryse.com/web/guides/get-started/trial-key>

### 7.2 Foxit PDF SDK for Web（第二候補）

公式情報上、PDFページ内容の編集機能を持ち、次に対応するとされている。

- 既存テキストの編集
- テキストの追加
- 画像の編集
- ページオブジェクトの編集
- 段落ベースの高度な編集

構成面は次のとおり。

- PDF編集用のWASMモジュールが提供されている
- 機能はモジュール分割され、必要時にロードされる構成
- 編集モジュールには標準編集（standard edit）と高度編集（advanced edit）の区分があるとされ、利用可能な範囲がライセンスにより異なる

今回の用途を技術的に満たせる可能性が高いため、**第二候補**とする。

留意点は次のとおり。

- 本番利用には製品ライセンスが必要
- 静的配信のみで完結する構成にできるかは、実際の配置構成で確認が必要

参考（作業時に再確認すること）:

- <https://developers.foxit.com/products/web/>
- <https://developers.foxit.com/documents/development-guide/pdf-sdk-web/getting-started.html>
- <https://webviewer-demo.foxit.com/docs/developer-guide/main/features/the-edit-modules.html>

## 8. 判定変更（1回目）

初回判定と再検討後の判定を並べると次のようになる。

| 観点 | 初回判定 | 再検討後の判定 |
|---|---|---|
| 調査範囲 | OSS・無償JSライブラリ中心 | 商用JS/WASM SDKを含む |
| 既存本文の直接編集 | 実現手段が見つからなかった | 製品機能として存在することを確認 |
| 静的Web構成との適合 | 検討対象外 | クライアントのみ構成が案内されている |
| 技術的実現性 | 困難 | 条件付きで可能 |
| 運用可否 | 判定に至らず | 未判定（実機検証が必要） |
| 総合判定 | 運用困難 | 実現可能性あり（PoC未実施） |

重要なのは、判断が変わった理由である。

> **「以前の判断が間違っていた」のではない。**
>
> OSS中心の調査範囲では実際に運用困難だった。
> 調査範囲を商用JS/WASM SDKまで広げたことで、実現可能性が見つかった。
>
> ただし、ここで変わったのは**技術的実現性の見通し**であって、庁内での運用可否ではない。

したがって、初回判定は「調査範囲に対しては正しかったが、調査範囲そのものが狭かった」と整理する。

この整理は、今後同種の検討を行うときにも有効である。
「できない」と判断したときは、**その判断が技術の限界なのか、調査範囲の限界なのかを必ず区別する。**

## 9. 第2段階時点の結論（当時の記録）

> この章は、商用Web PDF SDK調査を終えた第2段階時点の判定である。現在の判定は「15. 現在の結論」を参照する。

当時の判定は次のとおりだった。

> **実現可能性あり（PoC未実施）**

技術的実現性と運用可否は分けて扱う。両者を混同しないことが、この文書で最も重要な点である。

| 区分 | 現時点の判定 | 根拠 |
|---|---|---|
| 技術的実現性 | 条件付きで可能 | 商用Web PDF SDKに本文直接編集機能が存在する（公式ドキュメント上の確認のみ） |
| 運用可否 | 未判定 | 日本語編集品質、閉域条件、ライセンス条件のいずれも実機検証していない |

「静的WebツールではPDF本文テキスト編集は不可能」という以前の判断は、**技術的実現性について**修正する。

技術的実現性を条件別に整理すると次のようになる。

| 条件 | 技術的実現性 | 補足 |
|---|---|---|
| OSS・無償ライブラリのみ | 困難 | 本文の直接編集を安定提供する部品が無い |
| 商用Web PDF SDK利用可 | 条件付きで可能 | 機能は存在。運用条件は未確認 |
| PDF.js / pdf-lib中心の自前実装 | 採用しない | 実質的にレイアウトエンジンの自作になる |
| Apryse WebViewer | 第一候補 | 静的配信・クライアント処理構成との適合性が高い |
| Foxit PDF SDK for Web | 第二候補 | 機能面で候補。配置構成は要確認 |

一方、運用可否については、次を明確に区別する。

> **「機能が存在する」ことと「自治体内の一般職員向けツールとして運用できる」ことは同じではない。**

運用可否を判定するための材料（10章の未確認事項）が揃っていないため、現時点では**未判定**とする。

したがって、本番実装へはまだ進まない。

## 10. 第2段階時点で確認できていたこと / 未確認事項（当時の記録）

### 10.1 調査で確認済みとしてよいこと

#### Apryse WebViewer

- テキスト・画像の編集、移動、削除が可能とされている

- 段落ベースの高度な編集機能が存在する

> 注意: 上記はいずれも各社の公開ドキュメント上の記載に基づく。実機で検証した結果ではない。

### 10.2 まだ確認できていないこと

最も重要なのは「機能一覧」ではなく、**実際の自治体業務で扱うPDFで正常に編集できるか**である。

#### (1) 日本語PDF

- 日本語テキストを自然に編集できるか
- 日本語の埋め込みフォントを扱えるか
- フォント置換時にレイアウトが大きく変わらないか
- 縦書き等の特殊なPDFをどう扱うか
- IMEでの日本語入力が編集パネル上で正しく動くか

補足: フォント置換（ローカルフォントへの差し替え）が起きると、同じPDFでも端末により見え方が変わりうる点は、各社ドキュメント上でも言及されている。庁内端末のフォント構成差は実機確認が必要である。

#### (2) PDF互換性

次の生成元で編集品質に差が出ないか。

- Word等から生成した一般的なPDF
- Adobe製品で生成したPDF
- 複合機等から生成したPDF
- フォント埋め込みPDF
- フォント非埋め込みPDF

なお、画像だけで構成されたスキャンPDFはOCRを必要とするため、今回の本文テキスト編集対象とは分けて考える。

#### (3) 配置・通信

- SDK一式を庁内Webサーバーへ配置できるか
- CDNや外部APIを必要としない構成にできるか
- 起動時・利用時に外部通信が発生しないか
- ライセンス認証に外部通信が必要か
- オフライン・閉域利用に対応するライセンス方式が存在するか

補足: ライセンスキーの方式によって外部認証サーバーへの通信要否が異なる可能性がある。閉域利用の可否に直結するため、**採否を決める前に各社へ正式確認する必要がある。** 現時点で断定はしない。

#### (4) ライセンス・調達

- 自治体内利用が可能なライセンス形態
- 利用者数・端末数・サーバー数等によるライセンス条件
- Content Edit 等の必要モジュールを含む費用
- 庁内配布・静的Web配信時の条件
- トライアルから本番への移行方法

> 価格については、公式な確認が取れない限り記載しない。推測で書かない。

#### (5) 利用者適合性

- 一般職員向けのUIとして成立するか
- 説明を読まずに概ね操作できるか
- 編集失敗時に元PDFを壊さない運用にできるか

PoCの結果により、次のいずれかを判断する。

- 要件が「既存本文の直接編集」のままか（白塗り＋重ね書きに下がっていないか）
- 対象外機能（ページ回転・挿入・削除）が増えていないか
- 閉域・外部通信なしの前提が維持されているか

### 12.3 未確認事項のうち、最初に潰すべきもの

優先度の高い順に次のとおり。

| 優先 | 確認事項 | 理由 |
|---|---|---|
| 1 | 日本語PDFでの実編集品質 | ここが不可なら他条件を検討する意味がない |
| 2 | 外部通信・ライセンス認証の要否 | 閉域要件に直結し、採否を左右する |
| 3 | 編集後PDFの他ビューア互換性 | 業務文書として配布できるかに直結する |
| 4 | ライセンス形態・費用 | 調達可否に直結する（価格は公式確認が必要） |
| 5 | 一般職員向けUIとして成立するか | 運用開始後の問い合わせ量に直結する |

### 12.4 やらないと決めていること

再開時に方針が揺れやすいため、明記しておく。

- 白塗り＋重ね書きを「PDF編集」と称して代替にしない
- PDF.js / pdf-lib を使って本文編集を自前実装しない
- PoCを飛ばして本番実装に入らない
- 価格を推測で記載しない

## 13. 第3段階: 自作PDFエンジンの技術検証（`idontlovepdf-engine`）

商用SDK PoCへ進む前に、別リポジトリ `YanTKYS/idontlovepdf-engine` で、PDF本文テキスト編集エンジンをブラウザ向けに自作する技術検証を行った。

第1段階で「自前実装は採用しない」としていたにもかかわらず検証したのは、当時の判断が **PDF.js / pdf-lib の上へレイアウトエンジンを積む前提** だったためである。実際に着手したのは、PDFの内部構造（xref・オブジェクト・コンテンツストリーム）を直接読み書きし、既存のテキスト描画命令だけを差し替える方式であり、当時想定していた実装とは範囲が異なる。

### 13.1 実PDFで成立を確認した項目

PDF構造の解析:

- classic xref
- xref stream
- `/Prev`
- `/XRefStm`
- FlateDecode
- Predictor
- Object Stream（`/ObjStm`）

本文の取り出し:

- ToUnicode CMap
- 日本語本文抽出
- 本文検索

暗号化PDF:

- Standard Security Handler R4 / AESV2
- Standard Security Handler R6 / AESV3
- Adobe系R6 `/O`・`/U` zero-padding互換
- `/P` permission判定

編集と保存:

- 非暗号化PDFでの既存文字置換
- incremental save
- save後のreopen
- 独立したPDF Readerでの表示確認

複数の省庁公開PDFでも、読み込みと本文抽出に成功している。

### 13.2 第1段階の想定との違い

第1段階で「自前実装は保守できる規模を超える」と判断した根拠は、いまも部分的に有効である。

| 第1段階で懸念した点 | 第3段階での実際 |
|---|---|
| 段落・行・文字送りの再計算が必要 | 既存の描画命令を置き換える方式では、レイアウト再構成を行わない範囲であれば不要 |
| 埋め込みフォントのサブセット問題 | 既存フォントのToUnicodeに存在する文字への置換であれば成立する。新規グリフの追加は未対応 |
| 実質的にレイアウトエンジンの自作になる | レイアウトエンジンは作っていない。PDF構造の読み書きに範囲を限定している |

つまり、第1段階の懸念は「PDF編集ツール一般」には当てはまるが、**範囲を限定した本文置換**には必ずしも当てはまらなかった。

### 13.3 現時点で自作engineが対応していないこと

- 暗号化PDFの再保存（再暗号化）
- 埋め込みフォントに存在しない文字への置換
- レイアウトの再構成（行送り・折り返しの再計算）
- フォントの新規埋め込み
- スキャンPDFのOCR

## 14. 判定変更（2回目）

第2段階時点の判定と、第3段階を経た現在の判定を並べると次のようになる。

| 観点 | 第2段階の判定 | 現在の判定 |
|---|---|---|
| 判断材料 | 各社の公開ドキュメント | 実PDFでの動作検証結果 |
| 技術的実現性 | 条件付きで可能 | あり |
| 実現方式の第一候補 | Apryse WebViewer（商用SDK） | `idontlovepdf-engine`（自作engine） |
| 商用SDKの位置付け | 第一候補・第二候補 | 自作engineが要求水準へ届かなかった場合の代替候補 |
| ライセンス・調達の必要性 | 採否の前提条件 | 当面不要（代替候補を採る場合に再検討） |
| 運用可否 | 未判定 | 未判定（変更なし） |

判断が変わった理由は、第1回の判定変更と同じ構造である。

> **「以前の調査が間違っていた」のではない。**
>
> 第2段階時点では、自作engineが実PDFで成立するという材料が存在しなかった。
> その後、`idontlovepdf-engine` で実PDFの検証が進み、判断材料が増えたことで評価が変化した。

商用SDKの調査結果そのものは有効であり、破棄しない。自作engineが要求水準へ届かなかった場合に、そのまま代替候補として使える。

なお、ここで変わったのも**技術的実現性**であって、庁内での運用可否ではない。

## 15. 現在の結論

現時点の判定は次のとおり。

> **実現可能性あり（自作browser engineで実PDF検証済み）**

技術的実現性と運用可否は分けて扱う。両者を混同しないことが、この文書で最も重要な点である。

| 区分 | 現時点の判定 | 根拠 |
|---|---|---|
| 技術的実現性 | **あり** | `idontlovepdf-engine` により、実PDFで本文抽出・日本語ToUnicode・R4/AESV2・R6/AESV3・xref stream・Object Stream・検索、および一部PDFで置換→保存→独立PDF Readerでの表示まで確認済み |
| 運用可否 | **未判定** | 複数の実PDFで動作したことと、一般職員が安定運用できることは別である |

実現方式の位置付けは次のとおり。

| 方式 | 現在の扱い | 補足 |
|---|---|---|
| `idontlovepdf-engine`（自作browser engine） | **第一候補** | 実PDF検証済み。外部通信・ライセンス条件の制約が無い |
| Apryse WebViewer | 代替候補 | 自作engineが要求水準へ届かなかった場合に検討する |
| Foxit PDF SDK for Web | 代替候補 | 同上 |
| PDF.js / pdf-lib中心の自前実装 | 採用しない | 判断は第1段階から変更しない |
| 白塗り＋重ね書き | 採用しない | 判断は第1段階から変更しない |

商用SDKを「不要」とは断定しない。現時点では、自作engineの方が構成上の制約が少ないため優先する、という位置付けである。

### 15.1 エンジンとUIの責務分離

第3段階を経て、責務を次のとおり分離した。

| リポジトリ | 責務 |
|---|---|
| `idontlovepdf-engine` | PDF解析・暗号化認証／復号・本文抽出・検索・置換・保存 |
| `idontlovepdf` | 一般職員向けPDF編集ツールのUI / UX |

`idontlovepdf` は engine の正式Release bundleだけを依存物として取り込み、engine の `src/` や内部モジュールを参照しない。詳細は `vendor/README.md` を参照する。

### 15.2 エンジン統合PoCの結果

`idontlovepdf` 側で、engine v0.2.0 の正式Release bundleを同梱し、静的Webツールとして次まで成立することを実ブラウザで確認した。

- 正式公開API（`PdfTextEditor` / `ENGINE_VERSION`）からのES Module読み込み
- PDF選択（ボタン / ドラッグ＆ドロップ）
- ブラウザ内での読み込みと本文テキストの認識
- 日本語本文の認識
- 暗号化PDFの空パスワード自動認証、およびパスワード入力による再試行
- PDF以外のファイル・破損データを選んでも画面が停止しないこと
- 実行時に外部通信が発生しないこと

この段階では、検索・置換・保存のUIは実装していない。

## 16. 現在の未確認事項

運用可否の判定に必要な材料は、まだ揃っていない。

### 16.1 PDF互換性

- 複合機・Adobe製品・Word等、生成元の異なるPDFでの成功率
- フォント非埋め込みPDFでの挙動
- 縦書き等の特殊なPDFでの挙動
- 大きなPDF（ページ数・ファイルサイズ）での処理時間

### 16.2 編集品質

- 埋め込みフォントに存在しない文字へ置換しようとした場合の扱い
- 文字数が変わる置換でのレイアウトの見え方
- 編集後PDFの印刷結果
- 編集後PDFの、他ビューアでの表示互換性（一部PDFでは確認済み。範囲の拡大が必要）

### 16.3 運用

- 一般職員が説明なしで操作できるか
- 編集に失敗した場合に元PDFを壊さない運用にできるか
- 庁内端末（ブラウザversion・フォント構成）の差異による影響
- IIS等への配置手順と更新手順
- 問い合わせ対応の体制と保守範囲

### 16.4 engineの公開API

- `/P` permission（本文の読み取り可否・変更の可否）を公開APIから取得する手段が無い。一般利用者向けの表示が必要になった場合は、engine側の公開API拡張として扱う。

## 17. 次フェーズ

> **「一般職員向け編集UIの設計」**

エンジン統合が成立したため、次は検索・置換・保存を一般職員向けUIとして設計する。

### 17.1 次フェーズで扱うこと

- 本文の検索UI
- 本文の置換UI
- 編集結果の保存（ダウンロード）
- 編集できない文字・PDFに当たった場合の案内
- 元PDFを壊さない操作フロー

engineのデバッグ用画面（text run一覧、object番号等）を、そのまま製品UIへ持ち込まない。エンジンとUIの責務分離を維持する。

### 17.2 次フェーズでも扱わないこと

方針は第1段階から変更しない。

- 白塗り＋重ね書きを「PDF編集」と称して代替にしない
- ページ回転・ページ挿入・ページ削除
- スキャンPDFのOCR
- 実装より先に運用可否を「可能」と断定すること

### 17.3 運用可否の判定へ進む条件

次フェーズのUIが成立したうえで、「16. 現在の未確認事項」が概ね解消してはじめて、運用可否の判定へ進む。
