# idontlovepdf

自治体内で一般職員が利用することを想定した「PDF編集ツール」。

PDFの処理は、同一開発者による別リポジトリ `YanTKYS/idontlovepdf-engine` が担当する。

| リポジトリ | 責務 |
|---|---|
| `idontlovepdf`（本リポジトリ） | 一般職員向けPDF編集ツールのUI / UX |
| `idontlovepdf-engine` | PDF解析・暗号化認証／復号・本文抽出・検索・置換・フォント埋め込み・保存 |

## 現在の段階

**試作版。PDFの文字を検索し、1件ずつ置き換え、変更前と編集中のPDFを見比べて、編集済みPDFとして保存できる。元のPDFのフォントに含まれていない日本語の文字へも置き換えられる。**

`idontlovepdf-engine` v0.5.1 の正式Release bundleと、編集用フォント BIZ UDGothic・BIZ UD明朝を同梱し、次の操作を一般職員向けの画面として提供する。元のPDFの書体に近い編集用フォントは自動的に選ばれ、利用者が選ぶ画面は無い（詳細は「編集用フォントについて」を参照）。

1. PDFを選択する
2. 直したい文字を検索する
3. 検索結果から1件を選ぶ
4. 新しい文字を入力する
5. 置換する
6. 変更前／編集中のPDFプレビューで結果を確かめる
7. 編集済みPDFを保存する

利用者がPDFの内部構造を理解する必要はない。画面にはPDF内部の情報（object番号、テキストの分割単位、フォント名等）を出さない。編集用フォントも利用者が意識する設定ではないため、フォントを選ぶ画面は設けていない。

確認できている範囲は「動作確認」の項に記載する。GitHub PagesとIISでの動作は未確認である。

## 判定

技術的実現性と運用可否は分けて扱う。

| 区分 | 判定 | 根拠 |
|---|---|---|
| 技術的実現性 | **あり** | 実PDFでの本文抽出・日本語ToUnicode・暗号化PDF・複数の描画単位にまたがる語句の検索・置換／保存に加え、元PDFのフォントに無い文字への置換（編集用フォントの埋め込み）まで確認済み |
| 運用可否 | **未判定** | 技術的な適用範囲は大きく広がったが、庁内IIS上での実業務PDFによる試行を継続して判断する |

検討の経緯と根拠は `docs/feasibility.md` に記録している。

## できること / できないこと

現時点でできること。

- PDFファイルを選択する（ボタン、またはドラッグ＆ドロップ）
- ブラウザ内でPDFを読み込み、本文テキストを認識する
- 本文の文字を検索する（部分一致）。PDF内部で複数の描画単位に分かれて記録されている語句も、続いた1つの文字列として検索できる
- 検索結果から1件を選んで置き換える
- **元のPDFのフォントに含まれていない日本語の文字へ置き換える**（元PDFの書体に近い編集用フォントで書く）
- 文字数が変わる置き換えを行う（PDFの作りによっては断られる。下記参照）
- 文字を削除する（置き換える文字を空欄にする）
- 変更前のPDFと編集中のPDFをその場でプレビューし、切り替えて見比べる
- 成功した置換の内容を、変更履歴として画面で確認する
- 編集済みPDFを `元の名前.edited.pdf` として保存する
- パスワード保護されたPDFで、パスワードを入力して開く
- エラーの内容を区分して表示する（パスワード、非対応形式、破損、使用できない文字、安全に置換できない箇所 等）

現時点でできないこと。

- 任意のPDFの任意の箇所を自由に編集すること（下の「置き換えられない場合」を参照）
- 「すべて置換」
- PDF上の文字を直接クリックしての編集、文字位置やフォントの変更
- 段落の折り返し直し（Wordのような再レイアウト）
- ページ回転・ページ挿入・ページ削除
- スキャンPDF（画像だけのPDF）の編集

### 置き換えられない場合

置換できるかどうかは、engineが対象の箇所ごとに判断する。本ツール側で文字数やフォントから可否を推測することはしない。**検索結果を選んでいれば、置換文字数にかかわらず「置換」を押せる。** 押した時点でengineが確認し、安全に書き換えられない場合だけ理由を区分して案内する。

| 場合 | 画面の案内 |
|---|---|
| 置換後の文字が、編集用フォントにも無い（外字・異体字等） | 置換できません（使用できない文字を表示） |
| PDFの作り（文字の並べ方・間隔の指定・縦書き等）により、書き換えると文字の配置が崩れる | この箇所は置き換えられません |
| 置換文字列が編集用フォントで描かれたとき、後続の文字と重なってしまう | この箇所は置き換えられません |
| パスワード等で暗号化されたPDF | 暗号化PDFの保存には現在対応していません |
| 文書側で変更が禁止されているPDF（`/P`） | 文書側で変更が制限されています |

いずれの場合も、別の箇所を選ぶか、元のファイル（Word等）からの修正を検討する。

安全に置き換えられない箇所を断るのは、engineの設計（fail closed）である。ずれたPDF・崩れたPDFを作らないことを優先しており、本ツール側でこれを迂回する処理は実装していない。**「同じ文字数なら必ず置き換えられる」わけではない。** 元のフォントに無い文字を編集用フォントで描く場合、その置換文字列自身が後続の文字と重なってしまうとengineが判断したときも、文字を縮小したり後続文字を動かしたりはせず、PDFを変更する前に断る。

### 編集用フォントについて

元のPDFへ埋め込まれたフォントは、その文書で実際に使った文字だけを含むことが多い。そのため「元のPDFに出てこない文字」へ置き換えるには、別のフォントが必要になる。本ツールは編集用フォントとして BIZ UDGothic・BIZ UD明朝（いずれもSIL Open Font License 1.1）の2書体を同梱する。

**元のPDFの書体に近い編集用フォントは自動的に選ばれる。** 本ツールは2つのフォントのデータをそのままengineへ渡すだけで、元のPDFの書体がゴシック系・明朝系のどちらに近いかを判定し、どちらの編集用フォントを使うかを決めるのはengineの役割である。本ツール側でこの判定は行わない。判定の元になるPDF内部の情報（フォント種別のフラグ等）は開発者向け詳細欄にのみ表示し、通常の画面には出さない。

- 元のフォントで書ける場合は、従来どおり元のフォントで書く。編集用フォントは必要なときだけ使われる。
- 元のPDFのフォントに無い文字への置換は、engineが後続の文字位置を安全に維持できると判断し、かつ置換文字列自身が後続の文字と重ならないと判断した箇所で行える。判断には元のフォントの文字幅がPDF自身から正確に読み取れる必要があり、読み取れないフォントや、安全な配置を判断できない箇所では断る。どの箇所が該当するかを利用者が意識する必要はない。
- 編集用フォントが実際に使われた場合、そのフォント（ゴシック・明朝のうち実際に選ばれた一方だけ）が保存するPDFへ埋め込まれるため、ファイルサイズが数MB増える。同じPDF・同じ書体系統で置換を繰り返しても、増えるのは1回だけである。
- 編集用フォントはリポジトリに同梱したファイルだけを使う。実行時にインターネットから取得しない。フォント選択もengine内部で完結し、外部（システムフォント、Local Font Access API等）を参照しない。
- 編集用フォントは2つとも読み込めた場合だけツールを使える。**どちらか一方だけが読み込めた場合に、もう一方だけの構成へ黙って縮退することはしない。** どちらか一方でも読み込めない場合、ツールはエラーを表示してPDFを受け付けない。確認する時点は次の2段階である。
  - **起動時**: いずれかのファイルが無い、サーバーが配信できない、中身が空 → その場でエラーになる
  - **最初のPDFを開いた時点**: 取得はできたが、フォントとして読めない（配信設定によりHTML等が返る、ファイルが壊れている等） → 編集画面を開かずエラーになる
- 太字・斜体・weight（文字の太さ）・stretch（字幅）に応じたフォントの切り替えは行わない。明朝・ゴシックの2系統の選択にとどまる。元のPDFと完全に同じフォントへ合わせる機能ではない。
- engine v0.5.1では、`/FontDescriptor` がPDF内に直接書き込まれている（indirect referenceではない）場合にも判定できるようになった。公開資料PDF `22550.pdf` の `/F3` はこの構造（inline `/FontDescriptor`、`/Flags` にSerif bit）であり、v0.5.1でBIZ UD明朝が選ばれることを技術的に確認している（詳細は `docs/feasibility.md`）。ただし、これは「あらゆる明朝系PDFを正確に判定できる」ことを意味しない。font名の文字列辞書やembedded font programの詳細解析による補助判定は行っておらず、`/FontDescriptor`・`/Flags` から判定できないPDFは引き続き `unknown` としてBIZ UDゴシックへ倒れる。

## 構成

```text
index.html                          ツール本体
css/style.css                       画面のスタイル
js/app.js                           画面とエンジンの接続
vendor/idontlovepdf-engine.js       idontlovepdf-engine v0.5.1 の正式Release bundle
vendor/fonts/BIZUDGothic-Regular.ttf 編集用フォント（BIZ UDGothic Regular 1.05）
vendor/fonts/BIZUDMincho-Regular.ttf 編集用フォント（BIZ UDMincho Regular 1.06）
vendor/fonts/OFL.txt                BIZ UDGothicのライセンス（SIL OFL 1.1）
vendor/fonts/OFL-BIZUDMincho.txt    BIZ UDMinchoのライセンス（SIL OFL 1.1）
vendor/manifest.json                同梱engine・フォントのversion/SHA-256（CI/保守用）
vendor/README.md                    取り込んだengine・フォントの情報と更新手順
docs/feasibility.md                 実現可能性の検討記録
reference/guide_context.md          開発ガイド `lg_toolkit_guide` の最小ガイド（参照用）
.github/workflows/ci.yml            CI（後述）
package.json                        CI/開発テスト専用の依存関係定義（後述）
scripts/ci/                         CIが実行するNode.jsスクリプト
.nojekyll                           GitHub PagesでJekyll処理を無効化する（後述）
```

**ツール本体の実行・配布にnpmは不要である。** npm・Node.js・playwright（`package.json`）はCI（後述）と開発時のテストのみで使う。esbuild、webpack、Vite、Parcel等のビルド環境も導入していない。service worker、WebAssembly、サーバー側処理も導入していない。

`idontlovepdf-engine` 側で生成済みのブラウザ向け1ファイルbundleを、そのままES Moduleとして読み込む。最終的にサーバーへ配置するのは `index.html`・`css/`・`js/`・`vendor/` の静的ファイルだけであり、`package.json` や `scripts/ci/` は配置しなくてよい。

### エンジンとの責務分担

検索と置換の対象・可否を決める処理は、すべてengineの公開APIへ任せている。

| 処理 | 担当 |
|---|---|
| PDFの解析、テキストの分割単位の判断、語句の検索（`searchText()`） | engine |
| 置換可否の判断（`checkTextMatchReplacement()`）、置換（`replaceTextMatch()`）、保存（`save()`） | engine |
| 元のフォントで書くか編集用フォントで書くかの判断、編集用フォント2種類のうちどちらを使うかの判断、フォントの埋め込み | engine |
| 画面表示、操作の順序、編集用フォントの読み込み、プレビュー、変更履歴、エラーの言い換え | 本リポジトリ |

本リポジトリでは、PDFの描画命令の解釈、テキストの分割単位の連結、フォントの中身の判定、object番号の参照といったPDF内部構造の判断を行わない。編集用フォントについても、`/FontDescriptor` や `/Flags`（Serifビット等）をPDFから読む処理、フォント名やresource名からゴシック・明朝を判定する処理は本リポジトリには実装していない。本体側の責務は、2種類のフォントのバイト列をengineへ渡すことだけである。

## 外部依存・通信

- 実行時に外部通信は発生しない。
- 外部CDN、外部フォント配信、外部API、ライセンスサーバー、analyticsのいずれも利用しない。
- 編集用フォントはリポジトリ同梱のローカルファイルを、同一originの相対URLで読み込む。
- PDFプレビューはブラウザ標準のPDF表示機能とBlob URLだけで行う。PDF.js等の追加ライブラリも、外部のPDFビューアサービスも利用しない。
- エンジンbundleはリポジトリへ同梱している。実行時にGitHub Releaseから取得する方式は採らない。
- 選択したPDF、入力した検索文字・置換文字・パスワードは、いずれもブラウザ内だけで扱う。サーバーへ送らない。

## 個人情報・機密情報の取り扱い

- PDFの内容、検索文字、置換文字を送信・保存しない。
- 変更履歴は画面に表示するだけで、localStorage、sessionStorage、IndexedDB、cookieのいずれにも保存しない。PDFを選び直すと消える。
- 入力したパスワードは処理中のメモリ内だけで扱う。同じくどこにも保存しない。
- パスワードや暗号鍵を画面へ表示せず、ログにも出力しない。

## 利用環境

静的HTTPサーバーからの配信を前提とする。HTTPSは必須ではない。

- GitHub Pages
- IIS等の庁内静的Webサーバー（通常HTTP・閉域運用を含む）

配置は、リポジトリの内容をそのまま公開ディレクトリへ置くだけでよい。サーバー側の設定要件は次の2点である。

- `.js` をJavaScriptのMIME type（`text/javascript` 等）で配信すること（IISの既定設定で満たされる）
- `.ttf` を配信できること（IISの既定設定で満たされる）。MIME typeを絞った構成の場合のみ、`.ttf` → `font/ttf` の登録を確認する

`.ttf` を配信できないと編集用フォントを読み込めず、ツールは「編集用フォントを読み込めませんでした。配置を確認してください。」と表示して起動を止める。この表示が出た場合は、`vendor/fonts/BIZUDGothic-Regular.ttf` と `vendor/fonts/BIZUDMincho-Regular.ttf` の両方が公開ディレクトリへ配置されているかと、上記のMIME設定を確認する。

GitHub Pagesでは既定でJekyllが動作し、`vendor/` ディレクトリが公開対象から除外される。これを避けるため、リポジトリ直下に `.nojekyll` を置いている。**削除しないこと。**

PDFプレビューはブラウザ標準のPDF表示機能を利用する。この機能が無効な環境では、プレビュー欄に案内を表示し、検索・置換・保存はそのまま利用できる。

### `file://` での直接起動について

`index.html` を `file://` で直接開く方式は、正式な運用形態としない。

ES Moduleはブラウザのセキュリティ制約により `file://` から読み込めないためである。この場合は画面上に案内を表示する。

## 使い方

1. 静的HTTPサーバー経由で `index.html` を開く
2. 「PDFを選択」からPDFを選ぶ（ドラッグ＆ドロップも可）
3. 状態表示が「成功」になり、認識した本文の件数とPDFプレビューが表示される
4. 「検索する文字」に直したい文字を入れて「検索」を押す
5. 検索結果から直したい1件を選ぶ（前後の文章で見分ける）
6. 「置き換える文字」に新しい文字を入れて「置換」を押す
7. プレビューが「編集中」へ切り替わるので、直った内容を確認する
8. 「編集済みPDFを保存」を押してダウンロードする

補足。

- 置き換える文字を空欄にして置換すると、選択した文字を削除できる。
- 置換は1件ずつ行う。置換のたびに同じ検索文字で検索し直すので、残りの件数を確認しながら進められる。
- プレビューの「変更前」「編集中」は何度でも切り替えられる。「変更前」は最初に選んだPDFそのままである。
- 「変更 N件」は、編集中のPDFへ実際に反映された置換の件数である。失敗した置換や、同じ文字への置換は数えない。
- 元のPDFファイルは変更しない。保存は `元の名前.edited.pdf` という別名で行う。
- パスワード保護されたPDFでは、まず空パスワードでの読み込みが自動的に試される。それで開けない場合のみパスワード入力欄が表示される。

## 動作確認

確認は「どの環境で」「どのPDFで」行ったかまで含めて記録する。未確認の項目を確認済みと書かない。

### 現在確認済み

静的HTTPサーバー配信 + Chromium（Playwrightによる自動操作）での確認。バージョンごとの確認経緯は `docs/feasibility.md` に記録する。本項は現時点で確認できている範囲だけを示す。

**engine v0.5.1・`22550.pdf` の実構造を再現した合成PDFによる確認。**

`22550.pdf`（沖縄県糸満市が公開している資料）の `/F3` は、v0.5.0では判定できなかった構造（CIDFont dictionaryの `/FontDescriptor` がindirect referenceではなく **inline dictionary** として書かれている）を持ち、`/Flags` の値は `6`（Serif bit true）である。この原因は`idontlovepdf-engine`側のGitHub Actions実PDF検証（GitHub-hosted runner。同リポジトリの `docs/serif-classification-diagnosis.md` に記録）で確定しており、v0.5.1はこの構造にも到達できるよう修正されている。同検証では、`22550.pdf` 本体に対して `令和 → しょ` で実際に `BIZUDMincho-Regular` が埋め込まれ、`令和 → 平成` は元fontのまま成功し、`令和 → しょうわ` は保存前に拒否されることまで確認済みである。

開発環境からは公開PDF `22550.pdf` の配布元へ引き続き到達できないため（後述の「未確認」参照）、本リポジトリでの確認は、`22550.pdf` の `/F3` と同じ構造（inline `/FontDescriptor`、`/Flags 6`、「令和8年度」を `TJ` 配列＋続く `Tj` で描く配置）を再現した合成PDFを用いた。実際に同梱した engine v0.5.1 bundle と実際の BIZ UDGothic / BIZ UD明朝 フォントファイルで、静的HTTPサーバー配信 + Chromium（Playwrightによる自動操作）により、本体UI（`index.html` → PDF選択 → 検索 → 置換 → 保存 → 再open）を通して確認した。

- [x] 「令和 → しょ」が成功し（`checkTextMatchReplacement()` が `allowed: true` / mode `fallback-font`）、保存後PDFへ実際に埋め込まれたfallback fontが `BIZUDMincho-Regular` であることを、保存後PDFのバイト列（`/BaseFont`）で確認した
- [x] **保存後PDFを、本体・engineとは無関係な独立実装（PyMuPDF/MuPDF、FreeTypeによる実際のglyph rasterize）でレンダリングし、「しょ」が実際にBIZ UD明朝（Serif系の字形）で描画されていることを画像で確認した。** 比較用に、engineがSans判定する合成PDF（`/Flags 32`）で同じ「令和 → しょ」を行いBIZ UDGothicを埋め込んだ画像とも見比べ、字形が明確に異なる（ストローク終端の処理等）ことを確認した。Playwrightのheadless Chromiumでは、本体のPDFプレビュー用iframe・トップレベルのPDF navigationのいずれも実際の描画を取得できなかったため（既知のheadless Chromiumの制約。`docs/feasibility.md` 参照）、独立したレンダラでの確認とした
- [x] 「令和 → 平成」（元のフォントで書ける経路、mode `single-run`）はfallback fontを埋め込まずに成功する

## エンジン・編集用フォントの更新

`vendor/README.md` の更新手順を参照する。要点は次のとおり。

1. `idontlovepdf-engine` で新versionをRelease
2. Release asset `idontlovepdf-engine.js` を取得し、`.sha256` と照合
3. `vendor/idontlovepdf-engine.js` を差し替え
4. `ENGINE_VERSION` の表示を確認
5. `idontlovepdf` 側で実ブラウザ回帰確認

engine versionと編集用フォントのversion・SHA-256は `vendor/README.md` で管理する。JavaScriptコードへ版数を書き写さない。実行時のversion表示にはbundleがexportする `ENGINE_VERSION` を使う。

編集用フォントは、engine側の開発・テストで使われているものと同じversionを保つ。勝手に別のフォント・別のversionへ差し替えない。

## 既知の制限

- GitHub Pages / IIS 上での動作は未確認（「動作確認」を参照）。
- PDFの作りによっては、元のフォントに無い文字への置換や、文字数が変わる置換を断られる箇所がある。engineが安全に書き換えられないと判断した場合で、本ツールでは迂回しない（「置き換えられない場合」を参照）。
- 編集用フォントが使われた場合、保存するPDFのサイズが数MB増える。
- 編集用フォントの自動選択は、明朝・ゴシックの2系統のみ。太字・斜体・weight・stretchに応じた切り替えは行わない。元のPDFと完全に同じフォントへ合わせる機能ではない。システムフォントの取得やLocal Font Access APIは使用しない。
- 編集用フォントを使った置換では、後続の文字の位置を動かさないことを優先する。置換後の文字列自身が後続の文字と重なってしまう場合は、PDFを変更する前に断る（「置き換えられない場合」を参照）。文字を縮小したり後続文字を動かしたりして無理に配置することはしない。
- 置換は1件ずつ行う。「すべて置換」は用意していない。
- 検索結果の表示は先頭100件まで。件数は全件を表示するが、それ以降を選ぶには検索する文字を長くして絞り込む。
- プレビューは確認用である。プレビュー上の文字を直接編集したり、置換した箇所へ自動でスクロールしたりはしない。
- 暗号化PDFは検索まで。編集結果の保存はengine側で未対応。
- `/P` permission（変更の可否）は、置換を試みた時点で判明する。読み込んだ時点では表示しない。
- スキャンPDF（画像のみのPDF）は本文テキストを持たないため対象外。

## CI

`.github/workflows/ci.yml` が、`pull_request`・`main`への`push`・`workflow_dispatch`で自動実行される。本体が**静的Webアプリとしての構成を壊していないこと**を確認する最小限のCIであり、engine内部のPDF処理テスト（Serif/Sans判定、置換安全性判定等）はここでは行わない。それはengine repository自身のCIの責務であり、責務を重複させない。

CIが確認する範囲は次の3点だけである。

1. **vendor整合性**（`scripts/ci/check-vendor-integrity.mjs`）: `vendor/idontlovepdf-engine.js`・`vendor/fonts/BIZUDGothic-Regular.ttf`・`vendor/fonts/BIZUDMincho-Regular.ttf` が、`vendor/manifest.json` に記録したSHA-256・サイズと一致すること。engine bundleがES Moduleとして読み込め、`ENGINE_VERSION` が `vendor/manifest.json` の記載（現在は `"0.5.1"`）と一致すること。
2. **静的構成**（`scripts/ci/check-static-structure.mjs`）: 必須の静的ファイルが揃っていること、`js/app.js` に構文エラーが無いこと、runtimeとなるHTML/CSS/JSに外部URLへの参照が追加されていないこと（README等の説明用URLは対象外）。
3. **browser smoke test**（`scripts/ci/browser-smoke.mjs`）: 静的HTTPサーバーをCI内で起動し、Chromium（Playwright）で `index.html` を開き、engine bundleのロード・Engine欄のversion表示・2種類のfontのHTTP取得・font読み込み完了後のPDF選択UI有効化・同一origin以外への要求が発生しないこと・console error/uncaught errorが無いことを確認する。実PDFの読み込みや検索・置換は行わない。

`22550.pdf` はCI fixtureとしてコミットしていない（配布元の都合でCIが壊れることを避けるため）。実PDFでの回帰確認は、引き続き「動作確認」に記載の手動・開発環境での確認とする。

CIが使う `package.json`（playwright）はCI/開発テスト専用であり、ツール本体の実行・配布には不要である。ビルド工程（bundler等）はCIにも導入していない。
