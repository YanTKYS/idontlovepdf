## 1. 背景

自治体内で、一般職員（情報部門職員に限らない事務職員）が利用する「PDF編集ツール」を検討している。

想定する利用場面は次のようなものである。

- 起案文書や通知文のPDFに残った誤字を直したい
- 日付や金額など、PDF内の一部の文字だけを差し替えたい
- 元のWord等の原本が手元にない、または原本を追跡できないPDFを補正したい

利用環境の前提は次のとおり。

- Windows端末、庁内ネットワークまたは閉域ネットワーク
- 標準ブラウザ
- IIS等による静的ファイル配信
- 利用者端末への追加インストールは求めない
- 外部通信、外部API、外部CDNを前提にしない

この前提は `reference/guide_context.md`（`lg_toolkit_guide` の最小ガイド）に沿う。

## 2. 当初要件

主目的は次の1点である。

> **既存PDF内の本文テキストを直接編集すること**

具体的には、既存PDF内の文字を選択して、次の操作を行い、編集結果をPDFとして保存できることを想定している。

- 修正
- 削除
- 置換

### 2.1 「本文テキスト編集」に含めないもの

以下は、今回求めている「既存PDF本文テキスト編集」とは明確に区別する。

| 手法 | 今回の扱い | 理由 |
|---|---|---|
| テキスト追記（新規テキスト要素の追加） | 対象外 | 既存本文そのものは変わらない |
| 注釈（アノテーション）追加 | 対象外 | 本文レイヤーではなく注釈レイヤー |
| 白塗り＋文字の重ね書き | 対象外 | 見た目を繕うだけで本文が残る。検索・コピーで旧文字が露出する |
| フォーム入力 | 対象外 | フォームフィールドがあるPDFにしか使えない |

要件を白塗り＋重ね書きに下げて「PDF編集可能」と扱うことはしない方針とする。

理由は次の2点である。

1. 旧文字がPDF内部に残るため、文字検索・テキストコピー・別ビューアでの表示で旧内容が露出しうる
2. 自治体文書として、見た目と実体が異なる状態を職員向けツールで量産すべきではない

### 2.2 今回の対象外機能

次のページ編集機能は、今回の検討対象に含めない。

- ページ回転
- ページ挿入
- ページ削除

### 2.3 別扱いとするもの

- 画像だけで構成されたスキャンPDF（OCRを必要とするため、本文テキスト編集とは分けて考える）

## 3. 初回検討（第1段階）

当初は、一般的なOSS JavaScriptライブラリを中心に検討した。

主な検討対象は次のとおり。

- PDF.js
- pdf-lib

### 3.1 これらで実現できること

- PDFの表示
- PDFの生成
- テキストの追加
- 注釈の追加
- フォーム入力
- 既存ページへの描画

### 3.2 これらで実現できなかったこと

既存PDF本文のテキストを、一般職員がWordに近い感覚で直接編集する用途には適さない。

技術的な理由は次のとおり。

- PDFの本文は「文字列」ではなく、フォント参照・座標・描画命令の集合として保持されている
- そのため「この文字を1文字消して別の文字を入れる」という操作が、既存ページ内容ストリームの再構築を伴う
- 段落・行・文字送りの再計算をライブラリ側が提供していないため、編集結果のレイアウト整合を自前で担保する必要がある
- 埋め込みフォントのサブセット（使用文字だけを埋め込んだ状態）では、新しく入力した文字のグリフが存在しないことがある
- 日本語では文字種が多く、サブセット問題の影響が大きい

これを自前で実装すると、事実上PDFレイアウトエンジンを作ることになり、庁内の小規模内部ツールとして保守できる規模を超える。

## 4. 初回判定

上記を踏まえ、初回は次の結論とした。

> **当初要件のままでは、静的Webツールとして運用困難**

補足として、次を方針とした。

- 白塗り＋重ね書き等に要件を下げて「PDF編集可能」と扱わない
- 要件を維持したまま、いったん保留とする

## 5. 再検討の理由

初回判定の後、次の疑問が残った。

> 「既存JavaScriptライブラリを利用する前提でも、本当に不可能なのか」

初回検討の調査範囲は、実質的に **OSS・無償ライブラリに限定** されていた。

つまり初回判定は、
「PDF本文編集が技術的に不可能」ではなく、
「**調査した範囲に、それを実現する部品が無かった**」という判定だった可能性がある。

そこで、調査範囲を次まで広げて再検討した。

- OSSに限らない
- 商用のWeb向けPDF SDK（JavaScript / WebAssembly）を含める

## 7. 候補SDK

### 7.1 Apryse WebViewer（第一候補）

公式情報上、Content Edit 機能により次が可能とされている。

- 既存PDFテキストの直接編集
- テキストの移動
- テキストの削除
- 画像の編集
- 編集後PDFの保存

構成面での適合性は次のとおり。

- WebAssembly等を利用し、PDF処理をクライアント側で行う構成（client only モード）が用意されている
- クライアントのみの構成では、静的WebサーバーでHTML / JavaScript / CSS を配信し、ブラウザ内でPDFを処理する方式が正式に案内されている
- サーバーサイドの変換処理を必要としない

今回の「静的Webツール」「閉域前提」という構成との適合性が高いため、**現時点の第一候補**とする。

留意点は次のとおり。

- Content Edit は追加ライセンス対象（既存のWebViewerライセンスキーに含まれない扱い）とされているため、採用時にライセンス条件の確認が必要
- Content Edit モードのテキスト編集パネルで正しくフォントを表示させるには、フォント定義（`font.json` 等）側の条件を満たす必要があるとされる

参考（作業時に再確認すること）:

- <https://docs.apryse.com/web/guides/edit/text-edit>
- <https://docs.apryse.com/web/guides/deployment-options>
- <https://docs.apryse.com/web/faq/webviewer-on-static-server/>
- <https://docs.apryse.com/web/guides/get-started/trial-key>

### 7.2 Foxit PDF SDK for Web（第二候補）

公式情報上、PDFページ内容の編集機能を持ち、次に対応するとされている。

- 既存テキストの編集
- テキストの追加
- 画像の編集
- ページオブジェクトの編集
- 段落ベースの高度な編集

構成面は次のとおり。

- PDF編集用のWASMモジュールが提供されている
- 機能はモジュール分割され、必要時にロードされる構成
- 編集モジュールには標準編集（standard edit）と高度編集（advanced edit）の区分があるとされ、利用可能な範囲がライセンスにより異なる

今回の用途を技術的に満たせる可能性が高いため、**第二候補**とする。

留意点は次のとおり。

- 本番利用には製品ライセンスが必要
- 静的配信のみで完結する構成にできるかは、実際の配置構成で確認が必要

参考（作業時に再確認すること）:

- <https://developers.foxit.com/products/web/>
- <https://developers.foxit.com/documents/development-guide/pdf-sdk-web/getting-started.html>
- <https://webviewer-demo.foxit.com/docs/developer-guide/main/features/the-edit-modules.html>

## 8. 判定変更（1回目）

初回判定と再検討後の判定を並べると次のようになる。

| 観点 | 初回判定 | 再検討後の判定 |
|---|---|---|
| 調査範囲 | OSS・無償JSライブラリ中心 | 商用JS/WASM SDKを含む |
| 既存本文の直接編集 | 実現手段が見つからなかった | 製品機能として存在することを確認 |
| 静的Web構成との適合 | 検討対象外 | クライアントのみ構成が案内されている |
| 技術的実現性 | 困難 | 条件付きで可能 |
| 運用可否 | 判定に至らず | 未判定（実機検証が必要） |
| 総合判定 | 運用困難 | 実現可能性あり（PoC未実施） |

重要なのは、判断が変わった理由である。

> **「以前の判断が間違っていた」のではない。**
>
> OSS中心の調査範囲では実際に運用困難だった。
> 調査範囲を商用JS/WASM SDKまで広げたことで、実現可能性が見つかった。
>
> ただし、ここで変わったのは**技術的実現性の見通し**であって、庁内での運用可否ではない。

したがって、初回判定は「調査範囲に対しては正しかったが、調査範囲そのものが狭かった」と整理する。

この整理は、今後同種の検討を行うときにも有効である。
「できない」と判断したときは、**その判断が技術の限界なのか、調査範囲の限界なのかを必ず区別する。**

## 9. 第2段階時点の結論（当時の記録）

> この章は、商用Web PDF SDK調査を終えた第2段階時点の判定である。現在の判定は「15. 現在の結論」を参照する。

当時の判定は次のとおりだった。

> **実現可能性あり（PoC未実施）**

技術的実現性と運用可否は分けて扱う。両者を混同しないことが、この文書で最も重要な点である。

| 区分 | 現時点の判定 | 根拠 |
|---|---|---|
| 技術的実現性 | 条件付きで可能 | 商用Web PDF SDKに本文直接編集機能が存在する（公式ドキュメント上の確認のみ） |
| 運用可否 | 未判定 | 日本語編集品質、閉域条件、ライセンス条件のいずれも実機検証していない |

「静的WebツールではPDF本文テキスト編集は不可能」という以前の判断は、**技術的実現性について**修正する。

技術的実現性を条件別に整理すると次のようになる。

| 条件 | 技術的実現性 | 補足 |
|---|---|---|
| OSS・無償ライブラリのみ | 困難 | 本文の直接編集を安定提供する部品が無い |
| 商用Web PDF SDK利用可 | 条件付きで可能 | 機能は存在。運用条件は未確認 |
| PDF.js / pdf-lib中心の自前実装 | 採用しない | 実質的にレイアウトエンジンの自作になる |
| Apryse WebViewer | 第一候補 | 静的配信・クライアント処理構成との適合性が高い |
| Foxit PDF SDK for Web | 第二候補 | 機能面で候補。配置構成は要確認 |

一方、運用可否については、次を明確に区別する。

> **「機能が存在する」ことと「自治体内の一般職員向けツールとして運用できる」ことは同じではない。**

運用可否を判定するための材料（10章の未確認事項）が揃っていないため、現時点では**未判定**とする。

したがって、本番実装へはまだ進まない。

## 10. 第2段階時点で確認できていたこと / 未確認事項（当時の記録）

### 10.1 調査で確認済みとしてよいこと

#### Apryse WebViewer

- ブラウザ上でPDF本文テキストを直接編集する機能が存在する
- テキスト・画像の編集、移動、削除が可能とされている

- テキスト編集用のWASMモジュールが存在する
- 段落ベースの高度な編集機能が存在する

> 注意: 上記はいずれも各社の公開ドキュメント上の記載に基づく。実機で検証した結果ではない。

### 10.2 まだ確認できていないこと

最も重要なのは「機能一覧」ではなく、**実際の自治体業務で扱うPDFで正常に編集できるか**である。

#### (1) 日本語PDF

- 日本語テキストを自然に編集できるか
- 日本語の埋め込みフォントを扱えるか
- フォント置換時にレイアウトが大きく変わらないか
- 縦書き等の特殊なPDFをどう扱うか
- IMEでの日本語入力が編集パネル上で正しく動くか

補足: フォント置換（ローカルフォントへの差し替え）が起きると、同じPDFでも端末により見え方が変わりうる点は、各社ドキュメント上でも言及されている。庁内端末のフォント構成差は実機確認が必要である。

#### (2) PDF互換性

次の生成元で編集品質に差が出ないか。

- Word等から生成した一般的なPDF
- Adobe製品で生成したPDF
- 複合機等から生成したPDF
- フォント埋め込みPDF
- フォント非埋め込みPDF

なお、画像だけで構成されたスキャンPDFはOCRを必要とするため、今回の本文テキスト編集対象とは分けて考える。

#### (3) 配置・通信

- SDK一式を庁内Webサーバーへ配置できるか
- CDNや外部APIを必要としない構成にできるか
- 起動時・利用時に外部通信が発生しないか
- ライセンス認証に外部通信が必要か
- オフライン・閉域利用に対応するライセンス方式が存在するか

補足: ライセンスキーの方式によって外部認証サーバーへの通信要否が異なる可能性がある。閉域利用の可否に直結するため、**採否を決める前に各社へ正式確認する必要がある。** 現時点で断定はしない。

#### (4) ライセンス・調達

- 自治体内利用が可能なライセンス形態
- 利用者数・端末数・サーバー数等によるライセンス条件
- Content Edit 等の必要モジュールを含む費用
- 庁内配布・静的Web配信時の条件
- トライアルから本番への移行方法

> 価格については、公式な確認が取れない限り記載しない。推測で書かない。

#### (5) 利用者適合性

- 一般職員向けのUIとして成立するか
- 説明を読まずに概ね操作できるか
- 編集失敗時に元PDFを壊さない運用にできるか

PoCの結果により、次のいずれかを判断する。

### 12.2 判断の前提を再確認する

- 要件が「既存本文の直接編集」のままか（白塗り＋重ね書きに下がっていないか）
- 対象外機能（ページ回転・挿入・削除）が増えていないか
- 閉域・外部通信なしの前提が維持されているか

### 12.3 未確認事項のうち、最初に潰すべきもの

優先度の高い順に次のとおり。

| 優先 | 確認事項 | 理由 |
|---|---|---|
| 1 | 日本語PDFでの実編集品質 | ここが不可なら他条件を検討する意味がない |
| 2 | 外部通信・ライセンス認証の要否 | 閉域要件に直結し、採否を左右する |
| 3 | 編集後PDFの他ビューア互換性 | 業務文書として配布できるかに直結する |
| 4 | ライセンス形態・費用 | 調達可否に直結する（価格は公式確認が必要） |
| 5 | 一般職員向けUIとして成立するか | 運用開始後の問い合わせ量に直結する |

### 12.4 やらないと決めていること

再開時に方針が揺れやすいため、明記しておく。

- 白塗り＋重ね書きを「PDF編集」と称して代替にしない
- PDF.js / pdf-lib を使って本文編集を自前実装しない
- PoCを飛ばして本番実装に入らない
- 価格を推測で記載しない

## 13. 第3段階: 自作PDFエンジンの技術検証（`idontlovepdf-engine`）

商用SDK PoCへ進む前に、別リポジトリ `YanTKYS/idontlovepdf-engine` で、PDF本文テキスト編集エンジンをブラウザ向けに自作する技術検証を行った。

第1段階で「自前実装は採用しない」としていたにもかかわらず検証したのは、当時の判断が **PDF.js / pdf-lib の上へレイアウトエンジンを積む前提** だったためである。実際に着手したのは、PDFの内部構造（xref・オブジェクト・コンテンツストリーム）を直接読み書きし、既存のテキスト描画命令だけを差し替える方式であり、当時想定していた実装とは範囲が異なる。

### 13.1 実PDFで成立を確認した項目

PDF構造の解析:

- classic xref
- xref stream
- `/Prev`
- `/XRefStm`
- FlateDecode
- Predictor
- Object Stream（`/ObjStm`）

本文の取り出し:

- ToUnicode CMap
- 日本語本文抽出
- 本文検索

暗号化PDF:

- Standard Security Handler R4 / AESV2
- Standard Security Handler R6 / AESV3
- Adobe系R6 `/O`・`/U` zero-padding互換
- `/P` permission判定

編集と保存:

- 非暗号化PDFでの既存文字置換
- incremental save
- save後のreopen
- 独立したPDF Readerでの表示確認

複数の省庁公開PDFでも、読み込みと本文抽出に成功している。

### 13.2 第1段階の想定との違い

第1段階で「自前実装は保守できる規模を超える」と判断した根拠は、いまも部分的に有効である。

| 第1段階で懸念した点 | 第3段階での実際 |
|---|---|
| 段落・行・文字送りの再計算が必要 | 既存の描画命令を置き換える方式では、レイアウト再構成を行わない範囲であれば不要 |
| 埋め込みフォントのサブセット問題 | 既存フォントのToUnicodeに存在する文字への置換であれば成立する。新規グリフの追加は未対応 |
| 実質的にレイアウトエンジンの自作になる | レイアウトエンジンは作っていない。PDF構造の読み書きに範囲を限定している |

つまり、第1段階の懸念は「PDF編集ツール一般」には当てはまるが、**範囲を限定した本文置換**には必ずしも当てはまらなかった。

### 13.3 第3段階時点で自作engineが対応していなかったこと（当時の記録）

- 暗号化PDFの再保存（再暗号化）
- 埋め込みフォントに存在しない文字への置換
- レイアウトの再構成（行送り・折り返しの再計算）
- フォントの新規埋め込み
- スキャンPDFのOCR

このうち「埋め込みフォントに存在しない文字への置換」と「フォントの新規埋め込み」は、engine v0.4.0 で対応し（15.5）、対応できる箇所は v0.4.1（15.6）・v0.4.2（15.7）で広がった。残りは現在も対応していない。

## 15. 現在の結論

現時点の判定は次のとおり。

> **実現可能性あり（自作browser engineで実PDF検証済み）**

技術的実現性と運用可否は分けて扱う。両者を混同しないことが、この文書で最も重要な点である。

| 区分 | 現時点の判定 | 根拠 |
|---|---|---|
| 技術的実現性 | **あり** | `idontlovepdf-engine` により、実PDFで本文抽出・日本語ToUnicode・R4/AESV2・R6/AESV3・xref stream・Object Stream・検索、および置換→保存→独立PDF Readerでの表示まで確認済み。v0.4.0 で、元PDFのフォントに無い文字への置換（fallback fontの埋め込み）も確認済み。v0.4.1 / v0.4.2 でその対応箇所が広がったことを確認済み |
| 運用可否 | **未判定** | 技術的な適用範囲は v0.4.0 → v0.4.2 で広がったが、複数の実PDFで動作したことと、一般職員が安定運用できることは別である。実業務PDFでの試行は継続中 |

実現方式の位置付けは次のとおり。

| 方式 | 現在の扱い | 補足 |
|---|---|---|
| `idontlovepdf-engine`（自作browser engine） | **第一候補** | 実PDF検証済み。外部通信・ライセンス条件の制約が無い |
| Apryse WebViewer | 代替候補 | 自作engineが要求水準へ届かなかった場合に検討する |
| Foxit PDF SDK for Web | 代替候補 | 同上 |
| PDF.js / pdf-lib中心の自前実装 | 採用しない | 判断は第1段階から変更しない |
| 白塗り＋重ね書き | 採用しない | 判断は第1段階から変更しない |

商用SDKを「不要」とは断定しない。現時点では、自作engineの方が構成上の制約が少ないため優先する、という位置付けである。

### 15.3 検索・置換・保存UI（本ツール v0.2.0）

> この節は v0.2.0 時点の記録である。検索・置換の実装方針は 15.4（本ツール v0.3.0）で置き換わっている。

エンジン統合の次の段階として、一般職員向けの編集操作を実装した。

利用者から見える操作は次の6つだけとし、PDFの内部構造を理解しなくても使えるようにしている。

1. PDFを選択する
2. 直したい文字を検索する
3. 検索結果から1件を選ぶ
4. 新しい文字を入力する
5. 置換する
6. 編集済みPDFを保存する

engine側の技術検証画面にあった text run 一覧・object番号・fontName等は、一般利用者向け画面へ出していない。

設計上の判断は次のとおり。

| 論点 | 判断 | 理由 |
|---|---|---|
| 検索の範囲 | `listTextRuns()` が返す各本文の中だけを対象とする | まとまりをまたぐ検索をUI側で組むと、engineのPDF解析ロジックを本体側へ複製することになる |
| 置換の単位 | 1件ずつ。「すべて置換」は用意しない | 誤置換を避け、まず安全な編集体験を成立させる |
| 置換の実行 | 毎回、現在のPDFから作り直した一時editorで行う | 置換に失敗しても、それまでの編集状態を壊さない |
| 成功の判定 | `save()` の結果を開き直せた場合だけ成功とする | 開けないPDFを利用者へ保存させない |
| 元PDF | 選択時のバイト列を保持し、編集では触らない | 元ファイルを壊さない。将来「最初からやり直す」を追加できる |
| 検索条件の変更 | 検索欄を書き換えた時点で、前の検索結果と選択を捨てる | 画面の検索欄と実際の置換対象がずれた状態を残さない |
| 同じ文字への置換 | PDFを書き換えず、その旨を伝える | 「変更 N件」を実際に変わった件数と一致させる |

実ブラウザ（静的HTTPサーバー + Chromium）で確認できた範囲は次のとおり。

| 対象 | 結果 |
|---|---|
| 通常PDF（非暗号化） | 検索 → 選択 → 置換 → 保存 → 開き直し → ダウンロードまで成功 |
| 同一箇所に同じ文字が複数あるPDF | 3件を別々の検索結果として区別し、選んだ1件だけを置換できた |
| 空欄への置換（削除） | 対象の文字を削除できた |
| 日本語PDF（ToUnicode CMap） | 日本語の置換に成功し、保存後も再度読み込めた |
| フォントに無い文字への置換 | 「この文字は置き換えられません」と案内し、編集状態は変わらなかった |
| 暗号化PDF（`/P` 変更禁止、R4 / R6の両方） | 検索は成功。置換時に「文書側で変更が制限されています」と案内 |
| 暗号化PDF（変更は許可、再保存が未対応） | 「暗号化PDFの保存には現在対応していません」と案内 |
| 保存したPDFの表示 | このツールとは独立したPDF実装（Chromium内蔵ビューア）で開き、置換後の文字が表示されることを確認 |

暗号化PDFの編集保存は、engine v0.2.0 が再暗号化に対応していないため成立しない。`2024_subsidy_koubo_outline.pdf` はこの区分に当たり、検索UIの確認用として扱う。

### 15.4 engine v0.2.1 への移行と実PDF結果（本ツール v0.3.0）

> この節は v0.3.0 時点の記録である。置換可否の判断方法は 15.5（本ツール v0.4.0）で置き換わっており、ここに書かれている「本体側での文字数による事前判定」と「置換ボタンの無効化」は現在の実装には無い。検索を engine の `searchText()` へ一本化した方針は現在も維持している。

v0.2.0 の実装は、`listTextRuns()` が返す各 run の中を本体側で `indexOf()` して検索していた。実PDFで確認したところ、この方式には次の限界があった。

| 実PDFで起きたこと | 原因 |
|---|---|
| 1文字の検索は成立した | 1文字は1つの run に収まることが多い |
| 2文字以上の語句が検索できないPDFがあった | PDF側が語句を複数の text run へ分けて記録しているため、どの run にも語句全体が含まれない |
| そのため複数文字の置換もできなかった | 検索できないものは置換対象にならない |

これは engine の不具合ではなく、**PDFの内部構造の判断を本体側でやろうとしていたことの限界**である。run をUI側で連結すれば見かけ上は検索できるが、それは engine のPDF解析ロジックを本体へ複製する行為であり、無関係な位置に描かれた文字どうしを誤って連結する危険がある。

engine v0.2.1 は、この判断を engine の責務として引き受ける高レベルAPIを追加した。

| API | 役割 |
|---|---|
| `searchText(query, password?)` | 内容ストリームが「続いている本文」と言える範囲だけを連結して検索する。1件ごとに `id` / `text` / `before` / `after` / `runCount` を返す |
| `replaceTextMatch(matchId, replacement)` | 検索結果1件を、またがっている run すべてに分配して置換する |

本ツール v0.3.0 で、本体側の run 走査・`indexOf()`・runId / start / end の管理・run全文の組み立てを廃止し、検索と置換をこの2つのAPIへ一本化した。

#### 実PDFでの結果

語句が複数の text run へ分かれて記録されている実PDF（LibreOffice Writer生成・IPAGothic埋め込み・本文346件）で、v0.2.0 相当の方式と v0.2.1 の `searchText()` を同じPDFに対して比較した。

| 検索文字 | 文字数 | v0.2.0 相当（run内 `indexOf`） | v0.2.1 `searchText()` |
|---|---|---|---|
| 「度」 | 1 | 7件 | 7件 |
| 「年度」 | 2 | 2件 | **6件** |
| 「申請期限」 | 4 | 1件 | **3件** |
| 「実績報告書」 | 5 | **0件** | **1件**（5つの run にまたがる） |

**v0.2.0 では1文字しか安定して検索できなかったPDFで、2文字以上を検索できるようになった。** 置換についても次を確認した。

| 操作 | 結果 |
|---|---|
| 複数runにまたがる同文字数置換（「実績報告書」→「事業報告書」） | 成功。保存後、本ツールとは独立したPDF実装（poppler）で置換後の文字を読み取れた |
| 空文字による削除（「（案）」→ 削除） | 成功 |
| 単一runの異文字数置換（「（案）」→「（事業案）」） | 成功（engine仕様どおり、引き続き可能） |
| 複数runにまたがる異文字数置換 | 実行しない。置換前に案内し、「置換」ボタンを押せない状態にする |

なお、利用者環境の実業務PDF（`2024_subsidy_koubo_outline.pdf`）そのものでの再確認は済んでいない。16.5 に未確認として残している。

#### 異文字数の複数run置換の位置付け

複数runにまたがる語句の異文字数置換は、engine v0.2.1 が `MULTI_RUN_LENGTH_CHANGE_UNSUPPORTED` として明示的に拒否する。

これは**一般的なバグではなく、現在の安全な対応範囲の外**として扱う。PDFでは文字の位置が元の文字数を前提に記録されており、文字数を変えると文字がページ上のどこへ落ちるかが変わる。engine はそれを推測で埋めずに拒否する設計であり、本ツールもその設計に従う。

本ツール側では、engine へ送ってエラーになるのを待たず、置換文字の入力中に文字数（Unicodeのcode point数）を比較して事前に案内する。利用者向けの文言は「この箇所は現在、同じ文字数への置換または削除に対応しています。」とし、multi-run・operand・TJ・CMap といったPDF内部の用語は画面へ出さない。engine 側の `MULTI_RUN_LENGTH_CHANGE_UNSUPPORTED` は、事前判定をすり抜けた場合の安全策として引き続き捕捉する。

#### PDFプレビューの追加

これまでは、置換した結果を確かめるにはいったん保存してPDFを開き直す必要があった。v0.3.0 では、変更前と編集中のPDFを画面上で切り替えて確認できるようにした。

| 論点 | 判断 | 理由 |
|---|---|---|
| 表示方式 | ブラウザ標準のPDF表示機能（`<iframe>` + Blob URL） | PDF.js等の追加ライブラリも外部ビューアも入れない。閉域運用の前提を崩さない |
| 表示対象 | `変更前` は `originalBytes`、`編集中` は `currentBytes` | プレビューのためにPDFを再生成しない |
| Blob URL | 変更前用・編集中用を別々に保持し、置換成功時に編集中側だけ作り直して古い方を解放する | 置換したのに古いPDFが表示されたままになる状態を作らない |
| 切替の表現 | `aria-pressed` と「（表示中）」の文字と枠で示す | 色だけで状態を表さない。キーボードでも切り替えられる |
| プレビューの役割 | 確認のみ | 文字クリック編集・自動スクロール・highlight overlay・座標取得は実装しない。必要性を確認してから検討する |
| 表示できない環境 | プレビュー欄に案内を出し、検索・置換・保存は継続 | プレビューが使えないことで編集機能全体を止めない |

あわせて、成功した置換だけを「変更 2件 / 1.「実績報告書」→「事業報告書」」のように画面へ表示する。セッション内の表示のみで、localStorage等へは保存しない。失敗した置換と同じ文字への置換は数えない。

#### 置換時の安全設計（v0.2.0 から維持）

置換は現在のPDFへ変更を積み上げず、毎回 `currentBytes` から作り直した一時 editor で行い、`save()` と開き直しに成功した場合だけ編集状態を進める。

処理が非同期であることによる取り違えも、あわせて塞いだ。PDF解析は待ち時間を伴うため、その間に利用者が検索欄・置換欄・検索結果の選択を変えられると、画面の表示と実際の処理対象がずれる。対策は二重にしている。

| 層 | 内容 |
|---|---|
| 操作を止める | 処理中は、ボタンだけでなく検索欄・置換欄・検索結果（`fieldset`）も無効にする |
| 値を写し取る | 非同期処理の開始時に検索文字・選択位置・置換文字を局所変数へ写し、途中で画面や共有変数から読み直さない |
| 世代を確認する | 検索完了時に検索欄が同じ文字のままかを確認し、違っていれば古い結果を画面へ出さない |

特に置換では、選択位置を開始時に固定することが重要である。固定せずに一時 editor 側でその時点の選択位置を読み直すと、前後の文脈が同一の箇所が複数あるPDF（同じ書式の条文が並ぶ様式など）で、利用者が最初に選んだ箇所とは別の箇所を置き換えうる。実PDFで再現し、修正後は選んだ箇所だけが置き換わることを確認した。

v0.2.1 で1点追加した注意がある。**match ID は、それを発行した `PdfTextEditor` インスタンス専用である。** 画面で取得した match ID を一時 editor へ渡すと `UNKNOWN_MATCH` になる（実際にそうなることを確認した）。そのため一時 editor 側で同じ検索文字を `searchText()` し直し、選択していた順番の結果を取り直したうえで、件数・`text`・`before` / `after` が一致することを確認してから置換する。一致しない場合は「検索結果が変化しました。もう一度検索してください。」として中止する。match ID の文字列を解析して対応付けることはしない。

### 15.5 engine v0.4.0 への移行と編集用フォントの同梱（本ツール v0.4.0）

v0.3.0 までの最大の実用上の制約は、**元のPDFに埋め込まれたフォントに無い文字へは置換できない**ことだった。PDFへ埋め込まれるフォントは、その文書で使った文字だけのサブセットであることが多く、「令和」→「しょうわ」のように元の文書に出てこない文字を含む置換は、実PDFではほぼ通らなかった。

engine v0.4.0 は、この解決を公開APIとして提供した。

| API | 役割 |
|---|---|
| `setFallbackFont(fontBytes)` | 元のフォントで書けない文字用のフォントを渡す。engineは必要なときだけこれを使い、PDFへ埋め込む |
| `checkTextMatchReplacement(matchId, replacement)` | 置換可否を、何も変更せずに判定する。`{ allowed, mode }` または `{ allowed: false, code, reason, characters? }` を返す |

本ツール v0.4.0 での対応は次のとおり。

- 編集用フォントとして **BIZ UDGothic Regular 1.05**（SIL OFL 1.1）をリポジトリへ同梱した。engine側の開発・テストで使われているものと同じフォント・同じversionである。
- 起動時に同一originの相対URLで1回だけ読み込み、`Uint8Array` として保持して使い回す。実行時に外部から取得しない。
- 置換に使う一時 `PdfTextEditor` へ、置換の前に必ず `setFallbackFont()` を設定する。
- **本体独自の文字数制限（`lengthChangeBlocked()`）を撤去した。** 文字数・run数・フォント・PDF内部構造から置換可否を推測する処理は本体側に残していない。検索結果が選ばれていれば、置換文字数にかかわらず「置換」を押せる。
- 置換の直前に `checkTextMatchReplacement()` を実行し、`allowed: true` のときだけ `replaceTextMatch()` を呼ぶ。
- `mode`（`single-run` / `same-length` / `variable-length-safe` / `fallback-font-partial` 等）は開発者向け詳細にだけ表示し、一般利用者向け画面へは出さない。どのフォントで書くかの判断もengineへ委ねており、本体側でPDF内部のフォントを調べていない。

#### 確認結果

静的HTTPサーバー + Chromium（Playwrightによる自動操作）で確認した。対象は IPAGothic のサブセットを埋め込んだ日本語PDFで、「し」「ょ」「う」「わ」は本文に無く、サブセットにも含まれていない。

| 操作 | 結果 |
|---|---|
| 「令和」を検索し「しょうわ」を入力 | 本体側の制限で「置換」ボタンが無効にならない |
| engineの事前確認 | `allowed: true` / mode `fallback-font-partial` |
| 置換 | 成功。編集中プレビューに「しょうわ」が表示される |
| 保存 → 再open | 成功。再openしたPDFから「しょうわ」を検索できる（置換した箇所に「令和」は残らない） |
| 独立したPDF実装（pdfminer.six / qpdf） | 「しょうわ」を読み取れる |
| ブラウザ標準のPDFビューア | 「しょうわ」が表示される。後続の文字の位置は変わらない |

ファイルサイズの挙動も確認した。

| 置換 | 保存後のサイズ変化 |
|---|---|
| 既存フォントで書ける置換（同文字数・異文字数・削除） | +約1.8KB（フォントは埋め込まれない） |
| 編集用フォントを使った1回目の置換 | +約3.0MB（フォント1本ぶん） |
| 同じPDFでの2回目以降の編集用フォント置換 | +約1.5KB（フォントは再埋め込みされない） |

`FALLBACK_EDIT_REQUIRES_SAVE` は、本ツールの「1置換ごとに保存し、開き直してから次の置換を行う」既存設計により、通常の操作では発生しない。この設計は v0.2.0 から維持しているものであり、v0.4.2 でも変更していない。

#### 編集用フォントでも置換できない場合

engine v0.4.0 は、安全に書き換えられないと判断した箇所を推測で埋めずに拒否する（fail closed）。確認できた主な条件は次の2つである。

| 条件 | engineのerror code | 本ツールの案内 |
|---|---|---|
| 置換後の文字が編集用フォントにも無い | `FALLBACK_FONT_MISSING_GLYPH` | 「置換できません」＋ 対象の文字を表示 |
| 置換後の文字の配置を安全に決められない構造で描かれている | `FALLBACK_OPERATOR_UNSUPPORTED` 等 | 「この箇所は置き換えられません」 |

後者は engine の適用範囲であり、不具合ではない。v0.4.0 時点では `TJ` 配列で描かれた箇所への fallback font 置換が一律にこの拒否対象だったが、v0.4.1 で対応した（15.6）。v0.4.2 では、そこで必要になる元フォントの文字幅を読み取れる範囲が広がった（15.7）。

engineが拒否した場合、本ツールは編集中PDF・変更件数・変更履歴・プレビューを変更しない。案内文にはPDF内部の用語（CMap、glyph、`Tj`、`TJ`、text matrix、writing mode、run、object番号）を出さない。「同じ文字数なら必ず置換できる」と読める説明もしない。

#### 編集用フォントを読み込めない場合

編集用フォントは v0.4.0 以降の実用性の中核であるため、読み込みに失敗したまま通常起動したように見せない。いずれの場合も「編集用フォントを読み込めませんでした。配置を確認してください。」と表示し、PDFの受け付けを止める。詳細欄には開発者向けの元errorを出す。外部フォントへ自動で切り替えたり、ネットワークから取得したりはしない。

確認は2段階で行う。**取得できたことと、engineが読めるフォントであることは別**だからである。配信設定によっては、`.ttf` の要求に対してHTML（エラーページ等）が200で返ることがある。

| 段階 | 確認内容 | 検出できるもの |
|---|---|---|
| 起動時 | 同一originの相対URLで取得し、応答が成功か・中身が空でないか | ファイルが無い、サーバーが配信できない、0 byte |
| 最初のPDFを開いた時点 | 読み込んだPDFのeditorへ `setFallbackFont()` を実行（`FALLBACK_FONT_INVALID` を捕捉） | TTFとして読めない（HTML等が返る、ファイルが破損） |

後者で失敗した場合は編集画面を開かず、保持していたフォントのバイト列を破棄して、起動時に読み込めなかった場合と同じくPDFの受け付けを止める。どのPDFでも結果は同じであるためである。処理時間は同梱フォントで100〜200ms程度で、PDFを開く処理の中に収まる。

フォントの取得は `cache: "no-cache"` で行う。`vendor/README.md` にフォントの更新手順を定めている以上、同じパスのまま差し替えたときに古いキャッシュを使い続けてはならない。変更が無ければ 304 となり、本文は転送されない。

### 15.6 engine v0.4.1 への更新（本ツール v0.4.1）

v0.4.0 では、元のPDFのフォントに無い文字への置換ができるのは、対象が `Tj` で描かれている場合に限られていた。PDFでは同じ本文が `TJ`（文字ごとの位置調整を挟む配列）で描かれていることも多く、その箇所は `FALLBACK_OPERATOR_UNSUPPORTED` として拒否されていた。実業務PDFでどの程度当たるかが、v0.4.0 時点の未確認事項として残っていた。

engine v0.4.1 は、`TJ` で描かれた箇所についても、置換箇所が占めていた幅を測り、`TJ` の位置調整で後続文字の位置を維持できると証明できる場合に限って fallback font での置換を認めるようになった。

本ツール側の対応は次のとおりである。

- 取り込んだのは Release bundle 1ファイルだけである（SHA-256 照合済み）。engineの `src/` や内部モジュールは複製していない。
- **`Tj` / `TJ` の判定、文字幅の計算、置換可否の判断を本体側へ一切追加していない。** 操作フローは `searchText()` → `checkTextMatchReplacement()` → `allowed: true` のときだけ `replaceTextMatch()` → `save()` → 再open のままである。
- `mode` も従来の `fallback-font` / `fallback-font-partial` / `fallback-font-multi-run` のままで、`TJ` 専用の `mode` は無い。画面表示も変えていない。
- v0.4.1 で追加された `FALLBACK_FONT_METRICS_UNAVAILABLE` と `FALLBACK_CHAR_SPACING_UNSUPPORTED` を、既存の分類（`replace-unsafe`＝「この箇所は置き換えられません」）へ追加した。engineの `reason` や内部用語は一般利用者向け画面へ出さない。
- `FALLBACK_OPERATOR_UNSUPPORTED` は v0.4.1 で意味が狭まり（主に `'` / `"`、および `Tj` と `TJ` をまたぐ箇所）、`FALLBACK_FOLLOWING_TEXT_POSITION_UNSAFE` は `Tj` 側の安全判定として残る。本体側では分岐を増やさず、どちらも同じ案内のままとした。

#### 確認結果

静的HTTPサーバー + Chromium（Playwrightによる自動操作）で、`Tj` / `TJ` / `'` と文字間隔の指定を混在させた日本語PDF（IPAGothicのサブセット埋め込み、本文7行）を対象に確認した。

| 操作 | 結果 |
|---|---|
| `TJ` で描かれた「令和」を「しょ」へ置換（同文字数・fallback font） | `allowed: true` / mode `fallback-font`、置換成功 |
| `TJ` で描かれた「令和」を「しょうわ」へ置換（異文字数・fallback font） | `allowed: true` / mode `fallback-font`、置換成功 |
| 保存 → 再open → 検索 | 置換後の文字を検索できる。置換した箇所に元の文字は残らない |
| 後続文字の位置 | 独立したPDF実装（pdfminer.six）で座標を比較し、置換の前後で一致することを確認 |
| 文字間隔の指定がある `TJ` 行 | 同じく置換でき、後続文字の位置も維持された |
| `'` で描かれた箇所 | `FALLBACK_OPERATOR_UNSUPPORTED` で拒否。「この箇所は置き換えられません」と案内し、編集状態は変化しない |
| `Tj` で描かれた箇所（従来経路） | mode `fallback-font-partial` で従来どおり置換できる |

既存機能（読み込み、日本語検索、複数runにまたがる検索・置換、同文字数／異文字数置換、削除、プレビュー、変更履歴、保存、再open、暗号化PDF、変更禁止PDF、編集用フォントの読み込み失敗、外部通信なし）も併せて確認し、退行は無かった。`README.md` の「動作確認」に一覧を記載している。

#### 分かったこと（利用者への影響）

engine が保証するのは「**後続の文字の位置を動かさない**」ことであって、「置換後の文字が後続文字と重ならない」ことではない。置換後の文字列が元より幅を取る場合、後続の文字と重なって見えることがある。位置を動かさないほうが文書全体としては安全であるため、engineの仕様として受け入れ、`README.md` の「既知の制限」へ1行で記載した。本体側で幅を推測して補正することはしない。

なお、この取り込みは技術的な適用範囲を広げるものであり、**運用可否は引き続き「未判定」である**。配信環境と実業務PDFでの確認は済んでいない。

### 15.7 engine v0.4.2 への更新（本ツール v0.4.2）

#### 背景

v0.4.1 で `TJ` で描かれた箇所への fallback font 置換が可能になったが、実PDF `22550.pdf`（糸満市が公開している資料）では次の結果になった。

| 置換 | 結果 |
|---|---|
| 「令和」→「平成」 | 成功（元のフォントで書ける通常の置換） |
| 「令和」→「しょ」 | 失敗。`FALLBACK_FONT_METRICS_UNAVAILABLE`。対象font `/F3` |

後続文字の位置を維持するには、置換箇所が占めていた幅、すなわち元フォントのglyph幅が必要である。v0.4.1 はこのPDFからその幅を正確に取得できず、推測せずに拒否した（fail closed）。

engine v0.4.2 は、PDF自身が書いているフォント幅情報を読む範囲を広げた。従来のdirect valueに加えて、`/Widths`・`/W`・`/DW`・`/FirstChar`・`/MissingWidth`・`/DescendantFonts`・`/Encoding /Identity-H`・indirect numberのreal value 等が indirect object として書かれている場合も、既存のPDF object resolverで解決する。

#### 本ツール側の対応

- 取り込んだのは Release bundle 1ファイルだけである。Release assetのSHA-256が `.sha256` の値および Release 記載の値と一致することを確認したうえで差し替えた（`5255897b96d85a0d5eade796820fafc7641944e95f089515dcb9f44bc31841df` / 527,397 bytes）。engineの `src/` や内部モジュールは複製していない。
- **`/F3`・`/Widths`・`/W`・`/DW`・CID・`Tj` / `TJ`・font metrics・PDF objectを読む処理を本体側へ一切追加していない。** 操作フローは `searchText()` → `checkTextMatchReplacement()` → `allowed: true` のときだけ `replaceTextMatch()` → `save()` → 再open のままである。
- error codeの分類も変えていない。`FALLBACK_FONT_METRICS_UNAVAILABLE` は v0.4.1 から引き続き `replace-unsafe`（「この箇所は置き換えられません」）として扱う。PDF内部構造による新しい分岐は追加していない。
- v0.4.2 が返すようになった開発者向けの `unsafeReason` は、「詳細（開発者向け）」欄にだけ載せた（`showRefusal()` の1行）。一般利用者向け画面には出さない。`w-unresolved` / `widths-unresolved` / `non-identity-encoding` / CID / CMap といった語を利用者へ見せる必要はないためである。**`unsafeReason` の値で画面の案内を分けることはしない。** 分類は引き続き `code` だけで行う。
- 編集用フォント（BIZ UDGothic Regular 1.05）は変更していない。フォント選択UIも追加していない。
- 画面のengine version表示は従来どおり `ENGINE_VERSION` から取得する。本体側へ版数を書き写していない。

#### 確認結果（開発環境で生成したPDF）

静的HTTPサーバー + Chromium（Playwrightによる自動操作）で、全64項目を確認し、NGは0件だった。対象は開発環境で生成した日本語PDFで、IPAGothicのサブセットを埋め込み、「し」「ょ」「う」「わ」は本文にも埋め込みフォントのサブセットにも含まれていない。`Tj` / `TJ` / `'`、文字間隔の指定、複数の描画単位に分かれた語句を混在させた。

| 操作 | 結果 |
|---|---|
| Engine表示 | `v0.4.2` |
| 「令和」→「平成」（元font・同文字数） | 成功 / mode `single-run` |
| 「令和」→「しょ」（fallback font・同文字数） | 成功 / mode `fallback-font-partial` |
| 「令和」→「しょうわ」（fallback font・異文字数） | 成功 / mode `fallback-font-partial` |
| `TJ` で描かれた箇所への fallback font 置換 | 成功 / mode `fallback-font-partial` |
| 後続文字の位置 | 独立したPDF実装（pdfminer.six）で座標を比較し、差 0.000 pt |
| 保存 → 再open → 検索 | 置換後の文字を検索でき、置換した箇所に元の文字は残らない |
| 独立したviewer | ブラウザ標準のPDFビューア（Chromium）および pikepdf で表示・読み取りができる |
| 編集用フォントの埋め込み | 元fontで書けた置換は +約0.4KB、fallbackを使った1回目は +約3.0MB、2回目以降は +約1.2KB |
| `'` で描かれた箇所 | `FALLBACK_OPERATOR_UNSUPPORTED` で拒否。編集状態は変化しない |
| 暗号化PDF（AES-256 / R6）・変更禁止PDF（`/P`） | 従来どおり区別した案内。編集状態は壊れない |
| 外部通信 | 同一origin以外への要求 0件 |

既存機能（PDF選択、ドラッグ＆ドロップ、読み込み、日本語検索、複数runにまたがる検索・置換、同文字数／異文字数置換、削除、変更前／編集中プレビューと切り替え、変更履歴、保存、再open、編集用フォントの読み込み失敗、置換不能時の一般利用者向け表示）にも退行は無かった。`README.md` の「動作確認」に一覧を記載している。

#### `22550.pdf` の再試験（未実施）

**開発環境から `https://www.city.itoman.lg.jp/uploaded/attachment/22550.pdf` へ到達できず（egress proxyが当該ホストを拒否）、実PDFでの再試験は行えていない。** 推測したPDFを用いて「実PDF確認済み」とはしない。次の手順は実機確認事項として残す。

成功した場合に確認すること: 編集中プレビューへの反映 / 後続の「8年度」等の表示位置にずれがないこと / 変更履歴への記録 / 保存 / 保存したPDFの再open / 保存後PDFでの「しょ」検索 / 対象箇所の「令和」が消えていること / ブラウザ標準PDFビューア等の独立viewerでの表示。

失敗した場合に記録すること: error code / 「詳細（開発者向け）」の内容 / `unsafeReason` / 対象font / 置換前後の文字。**その場合も本体側へ回避処理を追加しない。** engine側の次課題として切り出す。

比較確認として、同じPDF・同じ箇所での「令和」→「平成」（元fontで書ける通常経路）が従来どおり成功することも併せて確認する。

#### v0.4.2 でも解決できない幅情報の書き方（engine側の次課題）

`22550.pdf` そのものは確認できていないが、幅情報がindirect objectで書かれたPDFを開発環境で組み立て、どこまで解決できるかを公開API（`checkTextMatchReplacement()`）だけで確かめた。`/W` の**要素そのもの**がindirect referenceの場合に、v0.4.2 でも解決できない。

| フォント辞書の書き方 | v0.4.2 の結果 |
|---|---|
| すべてdirect value | 置換できる |
| `/DescendantFonts` がindirect | 置換できる |
| `/Encoding` がindirect（`/Identity-H`） | 置換できる |
| `/W` 配列**全体**がindirect | 置換できる |
| `/DW` がindirect | 置換できる |
| `/W` の幅がreal値（`1000.0`） | 置換できる |
| `/W` の範囲形式（`cFirst cLast w`） | 置換できる |
| `/Widths` 配列**全体**がindirect（simple font） | 置換できる |
| `/FirstChar` がindirect（simple font） | 置換できる |
| `/MissingWidth` がindirect（simple font） | 置換できる |
| **`/W` の幅の数値がindirect（`c [n 0 R]`）** | `FALLBACK_FONT_METRICS_UNAVAILABLE` / `unsafeReason: invalid-width-array` |
| **`/W` の幅の副配列がindirect（`c n 0 R`）** | 同上 |
| **`/W` の先頭CID番号がindirect（`n 0 R [w]`）** | 同上 |
| **`/Widths` の要素がindirect（simple font）** | 同上 |

つまり v0.4.2 は「`/W` / `/Widths` を指すindirect reference」は解決するが、「配列の中に現れるindirect reference」は解決しない。これはengine内部の課題であり、**本体側で対応しない。** `22550.pdf` の `/F3` がこの書き方に当たるかどうかは、実PDFを確認できていないため不明である。

#### 判定への影響

この取り込みは技術的な適用範囲を広げるものであり、**運用可否は引き続き「未判定」である**。`22550.pdf` の再試験も配信環境の確認も済んでいない。engine v0.4.2 の取り込み自体が正常であることと、実PDFでのGo/No-Goは分けて扱う。
